# Эксплуатация

## Переменные окружения
| Переменная | Назначение | По умолчанию |
|---|---|---|
| `DJANGO_SETTINGS_MODULE` | `config.settings.prod` (образ) / `dev` (локально) | prod в wsgi, dev в manage.py |
| `SECRET_KEY` | секретный ключ (обязателен в prod) | — |
| `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS` | домены сайта | localhost |
| `FRONTEND_URL` | публичный адрес (ссылки в письмах) | `http://127.0.0.1:8000` |
| `POSTGRES_HOST/PORT/DB/USER/PASSWORD`, `DB_CONN_MAX_AGE` | PostgreSQL (без хоста — SQLite) | — / 60 с |
| `REDIS_URL` | кэш и общие лимиты | локальная память процесса |
| `CELERY_BROKER_URL` | брокер очереди (пусто = задачи выполняются сразу, в процессе) | — |
| `EMAIL_BACKEND`, `EMAIL_HOST/PORT/USER/PASSWORD/USE_TLS`, `DEFAULT_FROM_EMAIL` | почта (по умолчанию письма печатаются в лог) | терминальный бэкенд |
| `GOOGLE_CLIENT_ID` | вход через Google | — |
| `THROTTLE_ANON`, `THROTTLE_USER`, `THROTTLE_AUTH` | лимиты запросов | 240/min, 1200/min, 60/hour |
| `WEB_CONCURRENCY`, `GUNICORN_THREADS`, `CELERY_CONCURRENCY` | размер процессов | 3, 4, 2 |
| `LOG_LEVEL`, `LOG_JSON` | логи (в prod всегда JSON) | INFO |
| `BEHIND_PROXY`, `SECURE_SSL_REDIRECT`, `SECURE_COOKIES`, `SECURE_HSTS_SECONDS` | HTTPS за прокси | proxy: да; остальное выкл. |
| `CORS_ALLOWED_ORIGINS` | если фронтенд на другом домене | — |
| `SENTRY_DSN` | ошибки в Sentry (нужен `pip install sentry-sdk`) | — |
| `SEED_DEMO` | загрузить демоданные при старте (compose) | 1 |

## Развёртывание
1. Соберите образ (`docker build -t bookcircle .`) — статика собирается при сборке.
2. Выполните миграции **одной задачей** (`migrate` в compose, `Job` в k8s), затем запускайте веб, воркер и планировщик.
3. Планировщик (`beat`) — строго один экземпляр.
4. TLS завершайте на балансировщике/ingress; включите `SECURE_COOKIES=1` и HSTS.
5. Обновление без простоя: сначала миграции (обратно совместимые: «расширить → перейти → сжать»), затем постепенная замена экземпляров веба. Откат — предыдущий образ.

## Резервные копии
- PostgreSQL: ежедневный `pg_dump` + непрерывная архивация WAL (или управляемый сервис с PITR). Храните копии вне хоста БД, шифруйте.
- **Раз в месяц тренируйте восстановление** в отдельную среду: копия, которую не восстанавливали, копией не считается.
- Redis: кэш не требует копий; брокер — `appendonly yes` (включено в compose).

## Мониторинг и оповещения
Пробы: `/healthz` (процесс жив), `/readyz` (БД и кэш отвечают). Логи — одна JSON-строка на запрос с `request_id`. Оповещения — см. [SCALING.md](SCALING.md#8-наблюдаемость).

## Типовые ситуации
| Симптом | Проверка |
|---|---|
| Письма не приходят | `EMAIL_BACKEND` не SMTP (письма лишь в логах `web`/`worker`); логи `worker`; задача повторяется 3 раза с паузой |
| Уведомления есть, писем нет | у пользователя выключено дублирование на email; нет брокера (`CELERY_BROKER_URL`) |
| Нет напоминаний о просрочке | запущен ли `beat`; вручную: `python manage.py remind_overdue` |
| 429 «Too Many Requests» | `THROTTLE_*`; для нагрузочного теста временно повысить |
| «Нет доступа» к админке | `python manage.py createsuperuser` (роль администратора выставляется автоматически) |
| Забыли пароль администратора | `python manage.py changepassword <login>` |

## Безопасность
**Реализовано:** хэширование паролей и валидаторы; токены; роли и проверки на сервере; ограничения БД; лимиты (приложение + nginx); защита сброса пароля (одноразовый код, хранится хэш, 5 попыток, 10 минут,
одинаковый ответ для любых email); отсутствие автопривязки Google по email; `nosniff`, `Referrer-Policy`, `X-Frame-Options`, COOP для окна Google; HTTPS-настройки за прокси; контейнер без root;
выгрузка и удаление данных; минимизация показа телефона.
**Рекомендуется до продажи:** подтверждение email, 2FA, аудит журнала действий, `pip-audit` в CI, пентест, CSP (потребует убрать встроенные стили), менеджер секретов,
ограничение доступа к `/admin/` по IP/VPN, шифрование резервных копий.

## Жизненный цикл данных
Журналы запросов храните ≈ 30 дней. Уведомления старше 90 дней стоит архивировать (команда не реализована). Удалённые аккаунты обезличиваются (`deleted-<id>`), история обменов у других участников сохраняется.
